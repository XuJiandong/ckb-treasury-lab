60-second CKB recap

Cell

The unit of state: capacity (CKB), data, a lock script and an optional type script.

Transaction

Consumes inputs, creates outputs. cell_deps are read-only references: a script can read them without spending them.

Lock & type scripts

Lock = who may spend the cell. Type = rules on how the cell is created, updated or destroyed. This design identifies each cell by its type script.

since & Nervos DAO

A relative since says “this input must be at least N blocks old”, which is how every waiting period is enforced. DAO deposits are locked CKB and provide the voting weight.

One config cell holds every parameter. All scripts read it, and emergent_halt = 1 stops them all.

A proposal is unique (Type ID) and locks up a bond. Status goes 0 proposal → 1 finalized → 2 passed.

A vote points at exactly one proposal: its args are the hash of the proposal's type script.

A counting cell certifies the sum of a slice of vote cells, referenced as cell_deps.

What the vote script reads

The proposal (it must still be status 0) and the voter's DAO deposits, all passed as cell_deps.

Proving ownership

An input with the same lock as the deposits must be unlocked. That proves the signer owns the deposits.

The vote cell

  • vote_amount = sum of the referenced deposits
  • must be ≥ minimal_vote_amount
  • lock = the voter, direction = YES or NO
  • deposits are only read, never moved

Why “older than the proposal”?

Every deposit must be created before the proposal. Otherwise someone could vote, withdraw, re-deposit and vote again with the same CKB. A re-deposit is always newer than the proposal, so it is rejected.

Withdrawing a vote simply means consuming the vote cell. Keep it alive until it is counted.

Vote cells pile up

Each vote cell's lock hash has a 2-byte prefix (0x0000 to 0xFFFF). There may be thousands of vote cells, too many for one transaction.

Split into hash ranges

Each counting cell covers an inclusive range [start, end] and references matching vote cells as cell_deps. Each one is its own small transaction.

The counting script checks

  • every lock prefix is inside the range
  • every lock is unique
  • same direction as the counting cell
  • each vote was cast less than vote_window blocks after the proposal
  • declared sum = real sum

Finalize adds them up

Ranges must not overlap, so no voter is counted twice. Counters may leave out tiny votes, so flooding the system with “dust” votes cannot force extra work.

Create. Type ID args make the proposal unique. The capacity is a bond ≥ minimal_proposal_capacity, which is what a proposer loses if the proposal is successfully challenged. Status 0, total_yes 0.

Finalize (initiator): relative since > vote_duration. YES counting cells with non-overlapping ranges, Σ ≥ yes_threshold, written to total_yes. Bond unchanged, lock becomes always-success so anyone can challenge, and origin_block_number = P.

Challenge (anyone): NO counting cells whose Σ ≥ total_yes. The finalized cell is burned and the bond goes to a lock used by the challenger's counting cells.

Veto (admin): an input unlocked by veto_lock_script_hash can burn a finalized proposal.

Pass: the finalized input's relative since > challenge_time. Status 1 → 2. Description, amount, recipient and origin can never be rewritten.

Grant: the passed cell is consumed with a treasury cell, and an output locked by recipient_lock_hash receives ≥ requested_amount.

Recycle (initiator): a proposal that never passes gets its bond back once relative since > vote_duration + challenge_time.

Timing: three block counts

vote_window, vote_duration and challenge_time are plain block counts, compared either with block numbers or with a relative since.

Late vote

Cast at P + vote_window + 5: the vote script accepts it (status is still 0), but the counting script rejects it (VoteOutsideWindow).

Counting too early

A counting cell created at block ≤ P + vote_duration makes finalize fail (CountingCellTooEarly).

Challenger's NO votes

Measured from origin_block_number with the same vote_window, so NO votes must be cast during voting. New votes are impossible after finalize.

Passing too early

Pass needs relative since > challenge_time (strict). At exactly F + challenge_time it is still rejected.

Why each rule exists

Deposits older than the proposal

No vote → withdraw → re-deposit → vote again.

Unique locks, no duplicate cell_deps

A voter or a deposit is counted once.

Non-overlapping hash ranges

Counting cells can be summed safely.

vote_window

The set of countable votes is fixed; late votes can't sway the tally.

Always-success lock after finalize

Anyone can challenge; the initiator can't block it.

challenge_time

Time for NO voters to be counted before passing.

Bond

Proposing costs something, and a challenger has an incentive.

minimal_vote_amount

Dust votes can't flood the system.

Veto & emergent_halt

Safety valves, held by the config's (multisig) lock.
